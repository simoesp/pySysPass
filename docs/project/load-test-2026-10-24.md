# Load test — 2026-10-24

Production-like stack on one host: the backend image (`DEBUG=false`, non-root),
the nginx frontend as the only published entry point, and MySQL 8.0 on a
private network. Load came from `scripts/load_test.py` through nginx. Each
virtual user signs in once, then loops over 45% account lists, 20% account
reads, 15% password reveals, 10% searches, 7% creates, and 3% updates. The
host has 8 CPUs; every container shares them. These results describe this
host and mix, not a capacity guarantee.

| Run | Users | Workers | Throughput | List p50 / p95 | Read p50 / p95 | Reveal p50 / p95 | Create p50 / p95 | Errors |
| --- | ---: | ---: | ---: | --- | --- | --- | --- | ---: |
| Before the N+1 fix (≈220 accounts) | 10 | 1 | 5.1 req/s | 3346 / 3533 ms | 180 / 268 ms | 274 / 345 ms | 305 / 368 ms | 0 |
| After the fix (≈450 accounts) | 10 | 1 | 49.3 req/s | 148 / 237 ms | 190 / 286 ms | 273 / 378 ms | 329 / 450 ms | 0 |
| After, backup at 20 s | 30 | 1 | 46.5 req/s | 486 / 944 ms | 560 / 1015 ms | 649 / 1091 ms | 984 / 1698 ms | 0 |
| After, backup at 20 s | 30 | 4 | 133.6 req/s | 165 / 300 ms | 186 / 328 ms | 289 / 427 ms | 349 / 524 ms | 0 |

Findings:

- Account lists and search issued about five queries per account (509 for 100
  rows), which made listing 3.3 s at 10 users. Listing now uses eager loading
  and per-request caches: 10 queries for any page size. A regression test pins
  this (`test_account_listing_queries_do_not_grow_with_rows`; 360 queries for
  50 rows before, constant after).
- One worker saturates near 47 requests/s for this mix; beyond that, latency
  grows with the queue rather than errors appearing. Four workers on this host
  gave 2.9× the throughput at similar latency to the 10-user, one-worker run.
  Set `WEB_CONCURRENCY` (read by uvicorn) to run several workers. Session
  revocation, runtime config, and pending 2FA state are shared through
  `/app/data` with file locks, so all workers in a container stay consistent.
- Password reveals and account writes cost about 270–350 ms even unloaded.
  Defuse's password-protected key derivation dominates, by design and as in PHP.
- A full backup (database dump plus files) took about 2.6 s during load and
  caused no errors.
- 30 simultaneous first sign-ins took 1.5–2.4 s (bcrypt plus Defuse) while
  other traffic continued.

## Large dataset and soak

Same host and stack, 4 workers (`WEB_CONCURRENCY=4`, new passthrough in
`scripts/e2e-stack.sh`). 36 accounts were created through the API, then copied
in SQL to 18,432 rows (valid Defuse ciphertext under the same master, so reveals
work). The load generator reused that dataset (`--seed-accounts 0`) and
refreshed tokens every 120 s, as the SPA does, to outlive the 300 s session
timeout. Search used a term matching 3,418 rows.

| Run | Users | Duration | Throughput | List p50 / p95 | Search p50 / p95 | Reveal p50 / p95 | Errors |
| --- | ---: | ---: | ---: | --- | --- | --- | ---: |
| 18k accounts, search unbounded | 10 | 60 s | 37.7 req/s | 114 / 382 ms | 905 / 1983 ms | 157 / 535 ms | 0 |
| 18k accounts, search paged | 10 | 60 s | 93.7 req/s | 98 / 175 ms | 104 / 185 ms | 133 / 222 ms | 0 |
| Soak, backup at 15 min | 20 | 30 min | 88.0 req/s | 210 / 379 ms | 210 / 378 ms | 264 / 441 ms | 0 |

Soak detail: 158,355 requests and 280 token refreshes, no errors. The vault grew
from 18,432 to 30,080 accounts during the run (11,098 creates). Throughput per
5-minute window: 94.0, 89.6, 91.4, 88.9, 81.5, 82.5 req/s, with p95 between 383
and 434 ms. The decline coincides with the 63% data growth; it was not isolated
further. A full backup of the grown database took 24.3 s and caused no errors.
Backend memory (all 4 workers) went from 457 MiB at start to 544 MiB after
5 minutes, then to 595 MiB at 30 minutes; the process count stayed constant.
This run cannot distinguish slow growth (caches, allocator) from a leak; a
longer run would be needed.

Findings:

- `GET /accounts/search` returned every match. At 3,418 matches a request took
  about 0.9–2 s and dragged down the whole mix. It is now paged like
  `GET /accounts` (default 100, maximum 500); list and search pages are ordered
  by date and then id, so rows with equal dates no longer shift between pages.
- With several workers and `AUTO_INIT_DB_ON_STARTUP` on an empty database,
  every worker applied the bootstrap schema at once. The losers failed with
  `Table 'account_data_v' already exists` and uvicorn stopped the server. The
  bootstrap now runs under MySQL `GET_LOCK` (a file lock elsewhere) and
  re-checks inside the lock. A MySQL test with four concurrent workers fails
  without the fix and passes with it; the 4-worker stack then started cleanly.

Not covered: datasets beyond about 30,000 accounts, runs longer than 30
minutes, multi-host deployments, network latency to a remote database, and
slow SMTP or LDAP.
